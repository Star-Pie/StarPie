## 1. 宏输入与 Alt 干扰

### 1.1 宿主额外 Alt / 修饰键输入

用户描述：即使选择空动作，也像是发生两次 Alt 点击；执行宏后文本闪动或选中。两种现象先建立关联对照，不能仅凭截图认定同一根因。

源码线索：

- `GestureController.cs` 的取消、结束和关闭路径调用 `ActionExecutor.ReleaseStuckModifiers()`。
- `ActionExecutor.cs` 的该方法枚举左右及通用 Alt、Ctrl、Shift、Win，对未处于按下状态的键同时经过 `keybd_event` 与 `SendInput` 发送抬起。
- 这证明存在额外修饰键抬起路径，不能直接据此声称已确认“两次完整 Alt 按下/抬起”。
- `WindowTaskbarHelper.ActivateWindow` 另有 Alt 激活兜底，但轮盘的 `WheelFocusSwitcher` 已使用明确不注入 Alt 的保守激活入口。必须追实际调用链，不能把所有现象归咎于该兜底。

实施前验证：用可替换的输入记录器覆盖空动作、Esc、外部取消、普通动作、宏动作和用户物理按住修饰键。检查会话收尾与动作队列先后关系，确认是否存在重复或延迟到达的抬起；修复应保留必要的按键释放能力。

### 1.2 宏菜单序列

截图第二步为“逐字输入 AE”。当前宏解析器把普通字母拆成文字单元，经 `Host.SendText` 到宿主 Unicode 输入；换行和 Tab 则单独使用按键。文本框能出现 AE，不能证明目标软件收到了 A、E 的物理按键语义。

先以现有 DSL 建立比较用例：

```text
HOTKEY: Alt
WAIT: 100
KEY: A
WAIT: 100
KEY: E
```

上述等待值仅作可调对照起点，不是对 EPLAN 成功率的保证。验收必须记录 Alt、A、E 各自按下和抬起，区分物理键序列与 Unicode 文字输入，检查宿主收尾是否穿插额外事件，并覆盖普通/管理员目标及中英文输入环境。编辑器应清楚区分“依次按键”和“输入文字”，优先复用现有 KEY/HOTKEY 能力。

## 2. 左键长按与拖动

当前已有全局 `LongPressOnlyTrigger`，但它限制所有触发，并不等同于本次“只有左键在启用长按时禁用移动唤出”的要求。

用户随后明确选择“继续长按计时，移动不提前呼出，到时仍呼出”。本轮按此实现，不做原生拖拽交接；左键短点击保留既有回放，轮盘显示后的移动选择保留。回归等待期间移动、超时、松键、取消、专属层及其他鼠标/键盘触发。不得通过全局关闭移动选择来掩盖左键冲突。

## 3. 触发时间下限降至 0 ms（追加）

用户要求把截图中的 200 ms 下限尽可能降低，并支持 0。

源码已确认存在三处需一起处理的约束：`SettingsWindow.xaml` 滑块 `Minimum="200"`、按 50 ms 吸附；`SettingsWindow.xaml.cs` 回填控件时把不大于 0 的值当作 450 ms；`GestureController.StartLongPressTimer` 同样把 0 回退为 450 ms。只改滑块下限不能完成需求。

- 将合法范围下限设为 0，支持低值细调；旧配置缺失字段时保持既有默认延迟，不自动把所有用户改成 0。
- 显式 0 在设置、保存、重载及计时链路中保持一致，含义为不主动等待的立即触发。负数、非有限值和缺失值需与合法 0 区分。
- 复用既有 UI 派发及会话代际守卫，不把窗口构造或等待放进输入钩子；0 ms 是配置等待时间为零，不是承诺实际呈现耗时为零。
- 与左键任务一起设计：显式选择 0 后，按下即被用于唤出，不能再靠等待时长区分同一按键的普通点击/拖拽。界面应清楚说明这一行为；非零长按继续保障正常点击和拖拽。
- 回归覆盖 0、最小正值、原 200 ms、默认值、保存重开、专属层路由、鼠标/键盘、仅长按、定格、快速松键、自动重复及过期计时回调。验收时分别观察设置等待与实测呈现延迟，不拿控件显示代替实际触发证据。

## 4. 电池自启动

报告环境写为 StarPie `2.0.0.0`、Windows 11 Insider `29695`，实际运行版本、任务路径和安装来源仍须核实。

beta.4 的 `AutoStartRegistration.BuildTaskXml` 已显式设置：

```text
DisallowStartIfOnBatteries = false
StopIfGoingOnBatteries = false
ExecutionTimeLimit = PT0S
```

因此任务重点为旧注册项是否沿用、更新后的 EXE 是否与任务一致，以及用户明确执行修复后的回读结果。初始化和普通浏览保持只读，不因升级擅自启用用户禁用的自启动，也不为此改写成 Windows 服务。

任务与 HKCU Run 并存需分别检查启用状态、路径、参数、权限和单实例交接；仅凭“任务被电池条件跳过”，不能推定 Run 项必然随之失效。保留两种机制的现有兼容边界，补齐安装升级及真实电源场景验收。

## 5. 定格悬停音效

记录取消区→二级、二级→一级、一级→二级、二级→空区→原二级、切换父菜单等路径的交互事件和音效请求。

- 宿主 `PluginInteractionSession.Update` 当前在 `expanded && sub < 0` 时把目标置为 None，需核对是否抑制了返回一级时应有的反馈。
- 音效插件分别处理 `SubmenuExpanded` 和 `SelectionChanged`；用户听到的两声也可能是展开声与悬停声叠加，须用事件记录区分，不直接认定两次动作执行。
- 只对当前实际命中扇区发布悬停反馈，空区取消候选；已经保留的子菜单不应因重新进入而重复播放展开反馈。不得简单关闭整类音效作为修复。

## 6. 轮盘层重命名（#226）

Issue：<https://github.com/Star-Pie/StarPie/issues/226>，核对时为 open / enhancement。

该需求指独立配置层的名称，不是增加三级至五级同心展开。

已发布源码已有 `WheelLayer.Name/DisplayName`、`RenameLayerBtn_Click` 和铅笔按钮；层下拉宽度固定为 95，可能影响长名称辨识，但尚未作实机布局复现。先检查反馈者版本、入口发现难度、名称显示与持久化，再完善现有实现，不新增重复名称字段或第二套重命名逻辑。相关弹窗与提示同时纳入四语言检查。

## 执行和验收边界

1. 先以发布候选复现 P1 项目，冻结输入事件记录与预期，再实施最小修复；左键隔离与零延迟触发联合设计、分别验收。
2. 主代理负责宿主输入、生命周期和跨模块整合；DeepSeek/MAX 可承担明确路径的定位或隔离小修复；测试矩阵与材料可由 Kimi/GLM 评议，遵守当前工具资格及最多两位工作者规则。
3. 宏与音效插件分别构建、测试和发行，不随宿主静默安装；优先保持现有 SDK 与配置兼容。
4. 每项建立基线失败与修复通过的行为证据，相关输入修改按项目要求独立复核；人工验证 EPLAN、实际鼠标操作、电池登录、主题与 DPI。
5. 本清单不授权修改系统任务、真实输入注入或新的提交、合并、标签、打包与发布；这些动作沿用用户当次授权及项目人工门禁。

宏输入修复的范围与候选见 [宏输入与 Alt 干扰修复](macro-alt-input-repair.md)。用户已确认仅逐字输入 AE 正常，按 Alt 显示记事本菜单访问键提示属于正常行为；EPLAN 菜单宏验收按用户要求跳过，不记为通过。左键与零延时的本轮契约见 [左键长按与零延时触发](left-longpress-zero-delay.md)。
